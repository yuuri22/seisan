# Basic認証は効くのか — 守り方の理屈

## 結論を先に

**いまの構成では、ほとんど意味がありません。**

理由はひとつです。**守りたいものが、Basic認証がかかる場所に無いから**です。

ただしこれは「Basic認証がダメな技術だ」という話ではありません。
置き場所を変えれば効きます。その線引きを理解すると、
これから何を足すべきかが自分で判断できるようになります。

---

# 1. 認証は「どこ」を守るのか

## 錠前は、扉にしかかからない

Basic認証は、**Webサーバーがファイルを渡すかどうか**を判定する仕組みです。
ブラウザが `index.html` をくれと言ったとき、
「合言葉は？」と聞き返し、合わなければ渡さない。それだけです。

つまり守っているのは、**アプリのコードが配られる経路**です。

## では、あなたの記録はどこにあるか

```
   ┌─────────────────────────┐
   │  GitHub Pages            │  ← Basic認証をかけるならココ
   │  index.html（アプリのコード）│
   │  ※ 記録は入っていない      │
   └─────────────────────────┘
                │
                │ ブラウザが読み込む
                ▼
   ┌─────────────────────────┐
   │  あなたのブラウザ           │
   │  共有キーを保存             │
   └─────────────────────────┘
                │
                │ 共有キーを添えて直接やりとり
                ▼
   ┌─────────────────────────┐
   │  Supabase                │  ← 記録があるのはココ
   │  日付・店名・金額・…        │
   └─────────────────────────┘
```

記録は Supabase にあります。
そして**ブラウザは Supabase と直接やりとりします。**
GitHub Pages は、その通信に一切関わりません。

**扉に錠をかけても、金庫は別の建物にある。** これが今の状況です。

---

# 2. なぜ効かないのか — 攻撃者の立場で考える

共有キーを手に入れた人が、記録を読もうとしたとします。

## 普通の人がやること

1. アプリのURLを開く
2. Basic認証を求められる
3. 通れない → あきらめる

ここだけ見ると、防げているように思えます。

## 分かっている人がやること

アプリを**まったく開きません。**
Supabase に直接話しかけます。

```
POST https://xxxxxxxx.supabase.co/rest/v1/rpc/warikan_pull
  apikey: （公開されているキー）
  { "p_key": "共有キー" }

→ 記録がまるごと返ってくる
```

このリクエストは、GitHub Pages を経由しません。
**Basic認証は一度も出番がありません。**

必要な材料は、共有キーと anon キーだけ。
どちらもアプリのコードを読まなくても、招待リンクから取れます。

## だから、こう言えます

> Basic認証は「アプリを見せない」ための仕組みであって、
> 「記録を守る」ための仕組みではない。

そしてこのアプリのコードは、**見られても困りません。**
中に鍵は入っていないからです。
困らないものを隠すために、手間と使いにくさを払うことになります。

---

# 3. Basic認証が意味を持つ、唯一の場面

ただし、**設計を変えれば効きます。**

以前ご相談した「値を埋め込んだ配布用ファイル」を思い出してください。
あれは、ファイルそのものに共有キーが入っています。

```
DEFAULTS = {
  url:   "https://xxxxxxxx.supabase.co",
  key:   "eyJ...",
  house: "a1b2c3d4-..."     ← これが入っている
};
```

このファイルを公開の場所に置いた場合、
**ファイルを手に入れること = 鍵を手に入れること**になります。

このときはじめて、「ファイルを渡さない」ことに意味が生まれます。
Basic認証が、記録を守る最前線になるわけです。

## それでも、おすすめしません

理屈のうえでは成立しますが、設計としては後退です。

| | 鍵を埋め込まない（いまの形） | 鍵を埋め込む＋Basic認証 |
|---|---|---|
| 鍵の在処 | 各自の端末だけ | サーバー上のファイル |
| 守るもの | 共有キー（122ビットの乱数） | Basic認証のパスワード |
| 破られ方 | 総当たり不可能 | パスワード次第 |
| 漏れたとき | キーを作り直す | ファイルごと差し替え |

**鍵を置かない構成のほうが、そもそも守るものが少なくて済みます。**
守るものを増やしてから錠をかけるより、置かないほうが強い。

---

# 4. Basic認証そのものの弱み

参考までに、仕組み自体の性質も挙げておきます。

**合言葉を毎回送る**
リクエストのたびに、利用者名とパスワードが送られます。
中身はBase64という「読みやすくした形」であって、暗号ではありません。
HTTPSなら通信路は守られますが、暗号化しているのはHTTPSであって
Basic認証ではない、という点は押さえておいてください。

**やめる手段がない**
ログアウトの仕組みがありません。
ブラウザを閉じるまで、合言葉は覚えられたままです。

**試行回数の制限がない**
仕組みとして持っていません。
サーバー側で別途用意しなければ、いくらでも試せます。

**ふたりで同じ合言葉を使うことになる**
誰が入ったのか区別できません。
片方だけアクセスを止める、ということもできません。

**そもそもGitHub Pagesでは使えません**
静的ホスティングのため、この機能がありません。
使いたければ Netlify、Cloudflare、自前のサーバーなどへ移す必要があります。

---

# 5. 一般則：層を重ねるのが有効な条件

「多層防御」という考え方はまっとうです。
ただし、**層が攻撃の通り道と交わっていなければ意味がありません。**

判断するときは、この3つを順に確かめてください。

### ① 守りたいものは、どこにあるか

このアプリなら Supabase の中です。
だから対策は、Supabase に届く経路にかけないと効きません。

### ② 攻撃者は、どの道を通るか

道が複数あるなら、**いちばん弱い道**が全体の強さになります。
Basic認証は「アプリ経由」の道を塞ぎますが、
「Supabaseに直接」の道が開いたままです。

塞いだ道の脇に、開いた道がある。これでは意味がありません。

### ③ その層が破られたら、何が起きるか

Basic認証を破られても、共有キーがなければ記録は読めません。
逆に共有キーを破られたら、Basic認証があっても読めてしまいます。

**共有キーが単独で成否を決めている。** これが今の構造です。
ならば、力を注ぐべきは共有キーの扱いのほうです。

---

# 6. 代わりに効くこと（効き目の大きい順）

## 1位：GitHubとSupabaseに二要素認証

**なぜ効くか**：この2つのアカウントは、いまの構成の親玉です。
GitHubを取られればアプリを差し替えられ、鍵を盗む仕掛けを埋め込めます。
Supabaseを取られれば、管理画面から記録が直接読めます。

**Basic認証との差**：Basic認証は攻撃者の入口をひとつ塞ぐだけ。
二要素認証は、すべてを一度に奪われる経路を塞ぎます。

**手間**：5分。効果は最大。ここだけは必ずやってください。

## 2位：独自ドメインを使う

**なぜ効くか**：`username.github.io` は、あなたの全プロジェクトで
ブラウザの保存領域を共有します。他のプロジェクトから共有キーを読めます。

独自ドメインにすると別のサイト扱いになり、この経路が消えます。

**手間**：ドメイン代（年1,000円程度）と、設定に15分ほど。

## 3位：ときどき共有キーを作り直す

**なぜ効くか**：鍵が漏れたかどうかは、普通は気づけません。
定期的に取り替えれば、漏れていた場合の被害が期間で区切られます。

**手間**：SQLを1行実行して、新しい招待リンクを送るだけ。

## 4位：そもそも公開しない

**なぜ効くか**：ファイルを直接渡す形なら、
差し替えられる余地も、保存領域を共有する問題も、まとめて消えます。

**代償**：更新のたびに配り直しになります。
GitHubでの管理を諦めるかどうかは、天秤しだいです。

## 番外：Basic認証

**効き目**：ほぼゼロ（いまの構成では）
検索避けや、無差別なスキャンを減らす程度の意味はあります。
入れて悪くはありませんが、**これで安全になったと考えるのは危険です。**

# 7. 本当に堅くしたいなら

もし「もっとしっかりした認証がほしい」という気持ちがあるなら、
向かうべき先は Basic認証ではなく、**Supabase Auth** です。

## 何が変わるか

いまは「鍵を持っている人＝正しい人」という仕組みです。
これを「**この人だから入れる**」に変えられます。

| | 共有キー（いま） | Supabase Auth |
|---|---|---|
| 本人確認 | なし。鍵があれば誰でも | メールアドレスで確認 |
| 誰が操作したか | 分からない | 記録に残る |
| 片方だけ止める | できない | **できる** |
| 鍵が漏れたとき | 作り直して両方に配り直す | その人だけ締め出す |
| 使い始めるとき | リンクを開くだけ | メールを受け取って認証 |

## いちばんの違いは「取り消せる」こと

いまの構成では、一度渡した共有キーを**相手から取り上げる方法がありません。**
できるのは、鍵ごと作り直して自分だけ移ることだけです。

Supabase Auth なら、その人の権限だけを消せます。
共同で使うものとしては、こちらのほうが筋が通っています。

## 代償

- 相手にメール認証をしてもらう必要があります（開くだけ、ではなくなります）
- 設定するSQLが2〜3倍になります
- 端末を変えるたびにログインが必要です

**いまの用途に必要かどうかは、正直なところ微妙です。**
ふたりで家計をつけるのに、ここまでの仕組みは過剰かもしれません。

ただ、もし将来「三人目が入る」「見るだけの人を作りたい」
「関係が変わったときに片方を外したい」という話が出たら、
そのときは共有キー方式では対応できません。移行を考えてください。

---

# まとめ

**Basic認証を足しても、記録は今より安全になりません。**
守りたいものが Supabase にあり、ブラウザはそこと直接話すからです。
アプリのコードを隠しても、その通信は止まりません。

対策を選ぶときは、この順で考えてください。

1. **守るものはどこにあるか** — Supabase の中
2. **そこへの道は何本あるか** — アプリ経由と、直接の2本
3. **いちばん弱い道はどれか** — 共有キーが漏れる道

**共有キーが単独で成否を決めています。**
だから、力を注ぐべきは共有キーの扱いです。
アカウントを二要素認証で固め、リンクを慎重に送り、ときどき作り直す。

錠前を増やすより、鍵をどう持つかのほうが効きます。
