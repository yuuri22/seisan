# セキュリティの確認結果

割り勘アプリのSupabase同期について、設計を読み直して検証しました。
**修正が必要な問題が2つ見つかりました。** SQLを直したので、貼り直してください。

---

## 結論

| | |
|---|---|
| 記録が第三者に読まれる危険 | 見つかりませんでした |
| 記録を勝手に書き換えられる危険 | 見つかりませんでした |
| 妨害・費用を負わされる危険 | **ありました（修正済み）** |
| 使い続けるうえでの弱点 | 3つあります（下記） |

守りの要は共有キーです。これはUUID（122ビットの乱数）で、
1秒間に1兆回試しても、当てるには宇宙の年齢よりはるかに長い時間がかかります。
**総当たりは現実的に不可能**と考えて差し支えありません。

---

## 見つかった問題

### 1. 知らないキーでも世帯が作られてしまう（重大・修正済み）

**何が起きるか**

修正前の設計では、`warikan_pull` に適当なUUIDを渡すと、
その世帯がその場で作られる仕組みになっていました。

APIキーはアプリのファイルに埋め込まれているため、
ファイルを受け取った人や、それが何かの拍子に流れた場合、
第三者の手に渡る可能性があります。

その状態で、でたらめなUUIDを大量に投げ込まれると、
**あなたのデータベースが無関係な行で埋まります。**
無料枠（500MB）を使い切れば、同期が止まります。

記録を読まれるわけではありませんが、
使えなくさせられる、あるいは費用を負わされる、という実害があります。

**どう直したか**

世帯は、あなたがSQLを実行したときに1つだけ作られます。
アプリからは作れません。知らないキーで呼び出しても、
「そんなキーはありません」と断るだけで、何も残りません。

あわせて、一度に送れる件数（3,000件）と、
1つの世帯が持てる件数（50,000件）に上限を設けました。

---

### 2. 記録のIDが世帯をまたいで衝突しうる（中程度・修正済み）

**何が起きるか**

修正前は、記録のIDだけが主キーでした。
アプリはIDを8文字のランダム文字列で作っているので、
別の世帯がたまたま同じIDを使っていると、
**あとから来たほうの記録が保存されません。**

しかも失敗が表に出ないため、記録が消えたように見えます。

自然に起きる確率は低いのですが、
悪意を持って大量のIDを先に埋められると、
狙って妨害することが理屈のうえでは可能でした。

**どう直したか**

主キーを「世帯 + ID」の組み合わせに変えました。
別の世帯が同じIDを使っていても、互いに影響しません。

## 直したついでに固めたところ

**未来の時刻を送られたときの対策**
更新時刻はアプリが決めて送るため、
遠い未来の日付を入れられると、その記録が二度と変更できなくなります。
送られた時刻に「明日まで」という上限をかけました。

**文字数の上限**
店名などに極端に長い文字列を入れられないよう、上限を設けました。

**関数の検索パスを固定**
`search_path` を空にして、テーブル名をすべて明示しました。
別の場所に同じ名前のものを置かれて差し替えられる、という手口を防ぎます。

**実行権限の整理**
関数は既定で全員に実行権が付くため、いったん取り消してから
アプリ用の権限にだけ渡し直すようにしました。

**消した印の掃除**
削除の印が残り続けないよう、90日を過ぎたものは片付けます。

## 直せない、あるいは直す必要のない弱点

ここからは仕様として受け入れる部分です。知っておいてください。

### 共有キーを持つ人は、すべてができます

読むことも、書き換えることも、全部消すこともできます。
このアプリには「見るだけ」の権限がありません。

ふたりで使う前提なので通常は問題になりませんが、
**関係が変わったときは、キーを新しくしてください。**
渡した相手の端末からアクセスを取り上げる方法は、それしかありません。

新しくする手順は、SQL Editorで次を実行するだけです。

```sql
insert into public.households (id) values (gen_random_uuid())
returning id as "共有キー";
```

出てきた値を自分の端末に入れ直せば、古いほうとは切り離されます。
（古い記録は引き継がれないので、先に控えを残しておいてください）

### 端末を見られたら、キーも見られます

共有キーはブラウザの中に平文で保存されています。
端末のロックを解除できる人なら、開発者ツールから読み取れます。

これはこのアプリに限った話ではなく、
端末そのものにロックをかけて守る、という筋の話です。

### 相手が入れた内容は、そのまま表示されます

同期する以上、相手の端末から届いた文字列が画面に出ます。
細工した文字列を送り込んで画面を乗っ取る手口（XSS）に備え、
**表示する箇所はすべて無害化してあります。** 確認済みです。

ただし、これは「相手が悪意を持った場合」の備えです。
そもそも共有キーを渡す相手は、信頼できる人に限ってください。

## APIキーについて

「APIキーがファイルに入っているのは危なくないか」という点について。

**危なくありません。** `anon public` キーは、公開される前提のものです。
このキーだけでは、テーブルに一切触れません。
共有キーが揃って初めて、記録にたどり着けます。

ただし、次の2点にはご注意ください。

- **`service_role` キーは絶対に使わないでください。** こちらは何でもできる鍵です
- **今後このプロジェクトに別のテーブルを作る場合は、必ずRLSを有効にしてください。**
  無効のまま作ると、そのテーブルはAPIキーだけで読めてしまいます

## やり直しの手順

1. Supabaseの **SQL Editor** を開く
2. 新しいSQLの中身を**すべて**貼って実行する
3. 結果に出た「共有キー」を控える
4. アプリの設定に入れ直す（相手の端末にも）

すでに記録を入れていた場合は、テーブルの作りが変わっているため、
先に古いものを消してから実行してください。

```sql
drop table if exists public.entries;
drop table if exists public.households;
```

消す前に、アプリの **設定 → 控えを残す** から
スプレッドシートに写しておくことをおすすめします。
